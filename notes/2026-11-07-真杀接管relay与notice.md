# 真杀接管：`relay` 与 `notice` 两处「伪造崩溃」换成真的

- **一句话价值**：把「进程被杀在投递中途」的证据从「重新排一次同一行」换成真的 `SIGKILL`，
  并钉住了只有真杀才留下的现场：**死宿主的 claim、`attempts = 0`、lease 还没到期**——接管只能因为那个 PID 没了。
- **适用场景**：任何「同一行被两个进程共管、失败后由谁收尾」的队列设计；也是「测试里模拟崩溃」怎么才算数的例子。
- **限制 / 未验证**：只在本机 node 22 + 单机同一个 hostname 上跑；跨机器（owner 里的 hostname 不同）依然
  只能等 lease 到期，这条路没测也没做。没接真 DSH、没上 CI。

## 伪造与真杀差在哪

| | 重新排一行（`FAIL_SETTLE` 式或直接再 enqueue） | 真的 `SIGKILL`（本轮） |
| --- | --- | --- |
| 行上有没有 claim | 没有，`owner = ''` | 有，是**死进程**的 `host:pid:n` |
| `attempts` | 1（走过失败结算） | **0**（谁都没结算） |
| 谁能让下一个宿主接手 | 失败路径自己释放了 | 只有「那个 PID 确实没了」 |
| 能证明什么 | 结算后重试是幂等的 | 结算**根本没发生**时也不重复投递 |

这两件事在代码里是两条不同的路：`Effects.fail` 释放 claim 并加 `attempts`；进程被杀则什么都不跑。
所以 `FAIL_SETTLE` 只能验第一条，第二条得真杀。

## 做法（四步，源码一个字没改）

1. fixture 加开关：`steer`／`inject` 把消息写进 Session 历史后 `process.kill(process.pid, 'SIGKILL')`
   （`HOLD_AFTER_STEER=1` / `HOLD_AFTER_INJECT=1`）。历史必须先落地——那是下一个进程判定「重复」的唯一依据。
2. 用例先断言死进程留下了什么：`owner` 末段是那个 PID、`lease_until > now`、`attempts = 0`、`error = ''`。
3. 再起一个宿主：它接管、读到历史、**不再投递**、把行结算掉——于是「文本/通知只到 Session 一次」与「行消失」同时成立。
4. 变异验证：把 `released()` 改成恒 false，只有两个新例红（2 failed / 7 passed），改回后 `sha256` 核对源文件。

前 3 步只是「看起来对」，第 4 步才说明这两个用例真的在被 `released()` 钉着——否则它们和原来重排队那两例没区别。

## 一句总结

**「重新排一次同一行」证不了「崩溃现场」——崩溃现场是没人收尾，而队列还敢把行交出去。**
