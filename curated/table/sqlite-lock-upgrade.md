# SQLite 多进程共用：写锁要抢在第一次读之前

- **一句话价值**：SQLite 事务里「先读、后写」会触发锁升级，而锁升级**不调用 busy handler**，你的
  `busy_timeout=5000` 等于没设，同伴一写就当场 `database is locked`。把最外层事务改成
  `BEGIN IMMEDIATE` 即可。
- **适用场景**：两个以上的进程/连接共用一个 SQLite 文件（多实例 worker、自建任务队列、
  桌面端多开、容器里跑两份同一服务）。
- **限制**：只在同机同文件验证过；NFS/SMB 共用文件、真两台机器没测（而且 WAL 在 NFS 上官方就不支持）。

## 现象：0 毫秒就失败

两个连接开同一个库文件：A 用 `BEGIN IMMEDIATE` 拿着写锁不放，B 在事务里「先 `SELECT` 再 `INSERT`」。

| 版本 | B 的结果 |
| --- | --- |
| 事务外层是 `SAVEPOINT`（等价 deferred `BEGIN`） | `FAILED after 0ms: database is locked` |
| 事务外层改成 `BEGIN IMMEDIATE` | `FAILED after 5017ms`（等满 5s 窗口才失败） |

第一个数字是关键：0 毫秒说明 busy handler 根本没被调用，`busy_timeout` 完全没参与。

## 为什么

SQLite 对「已经持有**读**锁的事务里再要**写**锁」这种升级不做等待——它不调 busy handler，
直接返回 `SQLITE_BUSY`。理由是等下去会和别的升级者互相卡死，所以干脆不等。

而 `SAVEPOINT`（以及 deferred `BEGIN`）是惰性的：第一次读才拿读锁，写的时候才升级。
如果你的 `atomic()` 帮助函数最外层就是 `SAVEPOINT`，那么**每一次变更**都在踩这个坑。

## 改法（两处）

1. 事务帮助函数 `atomic()`：`depth === 0` 时用 **`BEGIN IMMEDIATE`**（先拿写锁再干活），
   提交 `COMMIT`、失败 `ROLLBACK`；嵌套层仍是 `SAVEPOINT` / `RELEASE`——它们骑在外层已拿到的写锁上，
   不会再发生升级。
2. 构造函数：原来自己 `BEGIN IMMEDIATE`、里面又调 `atomic()`，改成两层事务，会报
   `cannot start a transaction within a transaction`。正确做法是把「读版本、建表、补列、迁移、写版本」
   **整段交给 `atomic()`**，由它自己拿锁；迁移失败要用的原始版本号提到闭包外的变量里。

## 代价（要提前认）

- **所有**最外层事务现在一进来就抢写锁，包括那些只读的事务（比如读后可能不写的方法）。
- WAL 下写者本来就只有一个，多进程会排队。能接受的前提是：事务里只有同步 SQLite 调用、
  持锁是毫秒级，且等待上限被 `busy_timeout` 卡住（不会因为同伴死掉而吊死）。
- 反过来说：**别把慢操作塞进事务**，否则别的进程会一路排队到超时。

## 怎么测（照这个形状写）

光断言「最终写进去了」测不出这个坑——deferred 版本在没人抢锁时也是绿的。要造三个例：

1. **等待并成功**：另一个连接先 `BEGIN IMMEDIATE` 卡住锁，被测进程跑事务；1.5s 后没报
   `database is locked` → 放开锁 → 退出码 0、事务耗时 ≥ 1.4s、行真的落库。
2. **对照组**：没人持锁，同样先读后写，耗时 < 1s。没有这一例，第 1 例可能只是测了「程序慢」。
3. **有界放弃**：锁一直不放，事务应在 ~5s 后以 `database is locked` 结束，**而且什么都没写进去**。

### 一个容易白测的细节：计时点

子进程里如果从 `new Store(file)` 开始计时，测出来只有十几毫秒——因为**开库本身也是写**
（建表/改 schema），等待全花在开库上了，计时点根本不在事务里。做法是握手：
子进程先输出 `ready`，等父进程从 stdin 发 `go`，再进事务并记录耗时。

### 怎么证明测试有用

把 `BEGIN IMMEDIATE` 变异回 `BEGIN`（其余不动），上面第 1、3 例必须变红、第 2 例（对照组）仍是绿的。
第 2 例在变异后还绿，才说明第 1 例抓的是「等待」而不是噪声。

## 未验证 / 存疑

- 真第二台机器、NFS/SMB：没测。
- 「长事务 + 多宿主」没有专门用例，只是靠「事务里只有同步 SQL」这条约定兜着。
- 迁移中途失败 + 多人抢锁的场景只靠阅读确认，没造用例。
