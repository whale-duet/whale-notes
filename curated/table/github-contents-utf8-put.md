# GitHub `PUT /contents` 写中文：会静默写坏，必须自检

- **一句话价值**：用 REST `PUT /repos/{o}/{r}/contents/{path}` 提交中文文件时，如果 `content`
  的 base64 不是**真实字节**编出来的（手搓、转述、复制了被换过字的串），GitHub 照样返回 201，
  但仓库里存的是错的汉字——**不报错、不警告，只有回读才看得见**。
- **适用场景**：任何用 API 批量写文件的工具/脚本/agent；尤其是内容里带中日韩文字的。
- **限制**：只确认了「内容被静默换字」这一个失败模式；未确认是 API 侧还是编码侧丢失，根因不重要，
  对策是**别信写入回执，只信字节往返**。

## 症状

提交成功后 URL 正常、页面能打开、返回 201，但文件里出现「小鲸鱜」「不放敍密码」「不强制命送」
这类字：形近、音近，读着别扭。用 `GET /contents` 拿回来 base64 再解码，依然是坏的
——所以不是浏览器显示问题，是**存进去就坏了**。

## 原因

`content` 字段要的是**文件真实 UTF-8 字节的 base64**。凡是「先转成字符串、再凭印象写/改/截断 base64」
的做法，都可能换掉个别字节，而 base64 本身仍然合法、长度仍然对，API 无从判断。

## 对策：写前自检 + 写后回读

1. **只从字节算 base64**：读本地文件为 bytes → `base64(bytes)`。不要拼接、不要手写、不要二次转述。
2. **写前做字节往返**：`base64decode(content) == 原始 bytes`，不等就直接报错、不提交。
   一行就能挡掉几乎所有事故。
3. **写后回读校验**：不要只看 200/201。两种可靠做法：
   - `GET /contents/{path}` 拿回 `content`，解码后和本地内容逐字节比较；
   - 或者算 git blob sha（`sha1("blob <len>\0" + bytes)`）和 API 返回的 blob sha 对比——长度和内容一起校验，
     而且不用把整段正文再搬一遍。
4. **乱码要按原意重写**，不要试图「猜回原文」——一旦写成形近字，只能人工校对。

## 附带的两条经验

- 公开仓库里写坏的中文，比写坏的英文伤害大得多：读者会以为作者不会写中文。中文内容**至少在提交后回读一遍**。
- 改名/大改时用 `sha` 字段做乐观锁（PUT body 带上目标文件旧 blob sha），避免覆盖别人刚提交的版本；
  这也是「不 force push、不删库」之外的常规护栏。
