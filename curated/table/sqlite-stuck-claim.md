# 任务是「跑完了但收尾写不进去」：错误别急着抹掉

- **一句话价值**：带 claim/租约的 SQLite 任务队列，handler 跑完那条 `DELETE`/`UPDATE`
  因为锁写不进去时，不许当场把记录改回 ready，否则队列「自己知道出事了」而牌子显示无事；
  正确契约是**卡住的 claim 只该让这件事多跑一遍，不该丢效果，也不该一直红着**。
- **适用场景**：自己拿 SQLite 当队列，用 `owner = 自己` 当占位（claim）、用租约防僵尸的 worker。
- **限制**：锁来源是伪造的 `SQLITE_BUSY`（同一个连接被拒），没造「另一个进程真握着写锁十几秒」的场景。

## 场景

一次 attempt 的形状是：`claim`（把 `owner` 写成自己，带租约）→ 跑 handler → `settle()`
（`DELETE` 或 `UPDATE` 收尾，遇 `SQLITE_BUSY` 退避重试若干次）→ 成功就清行，失败就 `failed()` 记账。

问题出在最后一步：**handler 明明跑完了（效果已经发生），收尾写却被锁挡住**，
退避用尽后 `settle()` 返回 false。此时行还留着 `owner = 我`、`attempts` 没变、`due` 没动。

## 两个把错误抹掉的坑

1. **同一 tick 内自我抹平**：`attempt()` 在 `failed()` 之后无条件重新读表。可那一行的状态一个字都没被写，
   读表只会说「1 waiting since …」，于是刚写下的 error 立刻被覆盖成 ready。
   结果是：队列内部记录里这件事是坏的，对外牌子说没事。
2. **下一 tick 误清 broken**：原来清理逻辑是「这一趟跑不了任何行 → 说明队列恢复正常 → 清掉 broken 标记」。
   但这条卡住的行 `owner` 正是自己、租约还没到期，**本宿主当然跑不了它**，
   于是「跑不了任何行的一趟」被当成「走通的一趟」，broken 被清掉，这个 kind 从此安静；
   而那条已经执行过、收尾失败的行走要等一个**没人会续的租约**到期才被重跑。

## 修法

- `attempt()`：`settle()` 返回 false 时，`failed()` 之后**直接返回**，不要再读表/发 ready。
- 清理 broken 之前先问一句：**本实例在表里是不是有一条自己的行，但不在「正在跑」的集合里？**
  （即：我 claim 了，却没在跑它。）有就别清。正在跑的集合里的行不算卡住，别的 kind 照常读表。

契约因此变得明确：卡住的 claim 的代价是**多跑一遍**——租约到期、行被接回来、handler 第二次跑通、
收尾写成功，记录自己回到 ready。不是效果丢失，也不是永久红灯。

## 怎么测（关键手法）

不要起新进程造真锁，做一个**只让收尾那两句 SQL 失败的假 Store**：
`prepare()` 返回的语句名匹配 `/^(DELETE FROM effect|UPDATE effect SET (owner = ''|attempts = attempts \+ 1))/`
时抛 `SQLITE_BUSY`（带 `code: 'SQLITE_BUSY'`，让识别函数认得出来），其余入队、`SELECT`、普通清理
照样打到真库。把剩余拒绝次数设成退避次数的上限（例如 7），正好走完「退避用尽 → 放弃」。

两个用例缺一不可：

1. handler 跑一次后仍 pending；记账的**最后一笔必须是 error**，且 detail 里**不能出现 waiting**
   （出现就说明它又把自己读回了 ready）。再空转两 tick，最后一笔还得是那条 error（broken 没被清）。
   然后假时钟跳过租约 → handler 第二次跑通，最后一笔变 ready / 无事可做。
2. **对照组**：一行正在 handler 里跑时，这一趟必须照常读表、记录仍是 ready。
   没有这一例，第 1 例可以用「只要 broken 有值就不清」这种粗暴写法蒙过去。

对照组的价值就在这里：**它让「修得过头」也会被抓住**。

## 未验证

- 退避是被同一个进程的同一个连接占锁；没造真跨进程持锁。
- 「租约已过但还能续」的情形没区分（那种情况行会被重跑，broken 自然清掉）。
- 跨机器共用文件（NFS/SMB）未测。
