# 变异红了整组，不等于用例写得好

**一句话价值**：一次变异把整组用例打红，通常只证明「这组用例共用一个前置」；要证明每条用例各自钉住了不同的保护点，得补一条能**只红其中几条**的变异。

**适用场景**：给多进程 / 崩溃接管 / 幂等这类「一个场景写成 3～5 条相邻用例」的测试做变异检查时，读红绿表的那一步。

**限制 / 未验证**：结论来自一个自建消息队列项目（Node 22 + vitest + 多进程夹具，85 文件 / 1288 用例）；只做规则变异（改 SQL、改判断），没上变异算子工具；「能分开红」是必要条件，不是覆盖充分的证明。

## 三轮的真实记录（同一个 spec 家族）

| 变异 | 结果 | 怎么读 |
| --- | --- | --- |
| 让 claim 永远赢（去掉存活门 + CAS 不再 fence） | 1 红 2 绿 | 只红「两宿主都发」那例：claim 那条断言承重，另两例走的是接管路径，不靠它 |
| `deliver` 在调 Source 之前就把 receipt 记成 `sent` | 2 红 1 绿 | 红的是两例接管，断言都是「崩溃后 receipt 应仍 pending」——深浅合适 |
| `withdraw` 什么都不删，只报成功 | 3 红（全红） | 三条都红在**同一行**：撤回之后查库，预期 receipt 还在 `pending`。分不出哪条在管什么 |
| 撤回改回 `DELETE`（把墓碑删掉） | 3 红（全红） | 同上，全红在「撤回后第一眼」；这是本轮最浅的一层 |
| 留墓碑，但 `add` 把 `withdrawn` 当空位重新入队 | 2 红 1 绿 | 红第 2、3 例的「再入队」断言，第 1 例绿——那会儿它的 receipt 已是 `sent`，`add` 本来就拒绝。这才把三例真正的分叉切出来 |

## 判读规则

1. **先看红的行号，不是红的条数。** 全红且落在同一个断言 = 这组用例只共用一个前置，变异打在夹具上，没打在各自的保护点上。
2. **全红就补一条变异。** 找一个「只影响其中一条路径」的差异点。上表最后一行就是这么来的：第 1 例的状态已经是 `sent`，另两例还是墓碑——把「墓碑算不算空位」单独变异，就能只红两例。
3. **要红在深处的断言。** 红在「第一眼」往往说明前置断言太靠前，把后面真正要钉的保护点（id 花掉、不会重发）挡住了。做法：第一眼只断言必要的（墓碑在），把承重断言放到再入队 / 第二次发送之后。
4. **变异必须还原并比对哈希。** 否则下一轮读到的是变异版源码，后面所有结论都不可信。

## 附带：变异脚本自身的两个坑

- 把带双引号的 SQL 塞进 TS 的双引号字符串里 → 源码 PARSE_ERROR，测试框架报 `0 test / no tests`，看着像「用例没被收集」，其实文件根本没编译。看到「no tests」先搜 `Transform failed` / `PARSE_ERROR`。
- 「no tests」和「用例全绿」在退出码上都是 0，别把前者当通过。

## 最小可操作版本

```sh
# 1) 跑一条变异，记录 红的用例名单 + 红在哪个断言
# 2) 若全红：翻用例，找一条「只在该例成立的差异」
#    —— 状态不同、顺序不同、谁先死不同，都算
# 3) 为这个差异单独写一条变异，重跑，期待「部分红」
# 4) 还原源码，sha256 前后一致
```

配套脚本见同目录 [`mutation-check.sh`](mutation-check.sh)（它只负责「改一处 → 跑 → 还原 → 出 RED/GREEN 表」，红的分布要自己读）。
